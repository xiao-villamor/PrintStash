# Native G-code metadata engine

PrintStash extracts text G-code and BGCODE metadata in Rust. The public Python
models and import behavior remain stable, while the format and numerical work is
available through the framework-independent `printstash-gcode-core` crate.

## Ownership and boundaries

| Concern | Owner in M08 |
| --- | --- |
| Text metadata parsing and bounded file reads | Rust `printstash-gcode-core` |
| BGCODE framing, parameters and checksums | Official Prusa libbgcode core behind `printstash-libbgcode` |
| Deflate and Heatshrink decoding | Stock zlib and upstream Heatshrink behind fixed adapter budgets |
| Python type translation | The narrow PyO3 `gcode` module |
| Import coordination and retries | Existing Python import stages |
| Durable job and Artifact state | Existing Python `BackgroundJob` and application transactions |

The Rust crates do not depend on Python, an ORM, an HTTP framework, a queue, or
an external service. The Python facade translates the native result into the
existing immutable `GcodeMetadata` model and makes no format decisions. M08 does
not change HTTP contracts, the import coordinator, durable ownership, or the
stored metadata shape.

The native extension remains a required local dependency for the backend, as it
already was for mesh processing. A missing or incompatible extension fails the
application dependency check instead of silently selecting a second parser.

## Established dependencies

BGCODE support uses Prusa's libbgcode at commit
`d4da9073616d70a43c151e8c1d7fbff879d2e08a` (upstream version `0.3.0`). Upstream
does not publish release tags, so the full commit and the verified source archive
SHA-256 are its version identity. That commit matched upstream `main` and `HEAD`
when M08 started on 2026-09-18. Heatshrink `0.4.1`, the latest stable upstream tag
verified on the same date, supplies the format's 11/4
and 12/4 codecs. `libz-sys` supplies stock zlib for deflate, and CXX supplies the
Rust/C++ boundary. Exact versions, source hashes, included files, licenses, and
the update procedure are recorded in `backend/rust/libbgcode-sys/VENDOR.md` and
the workspace lockfile.

The directly selected crates were also rechecked against crates.io on
2026-09-18: CXX `1.0.202`, `libz-sys` `1.1.29`, regex `1.13.1`, and cc `1.4.6`
were the latest stable releases.

The adapter retains application safety policy that the upstream format library
does not provide. It does not reimplement BGCODE framing, checksum calculation,
deflate, Heatshrink, or printable G-code decoding.

## Resource and compatibility contracts

- Text files read at most 64 KiB from the head and 64 KiB from the tail. The
  middle of a large toolpath is never scanned for metadata.
- A BGCODE file may contain at most 4,096 blocks. Individual encoded blocks are
  capped at 64 MiB, decoded metadata at 8 MiB total, individual thumbnails at
  32 MiB, and decoded thumbnails at 64 MiB total.
- Metadata and thumbnail streams must decode to their exact declared length.
  Truncated streams, trailing deflate data, checksum failures, unknown block
  types, unknown codecs, invalid thumbnail parameters, and container overruns
  are rejected without an unbounded allocation.
- Metadata inspection skips the printable G-code payload. Full container
  validation streams every checksum through a fixed 64 KiB buffer.
- The parser retains the existing OrcaSlicer, PrusaSlicer, Bambu Studio,
  SuperSlicer, and Cura spellings, units, multi-tool order, and lossy UTF-8
  behavior. Missing or malformed metadata remains an empty result rather than an
  import failure.

libbgcode's INI metadata iterator does not advance past blank or non-key lines.
The adapter parses the already bounded, checksum-verified, exactly decoded
metadata bytes so hostile uploads cannot hang the process. This local policy
also synthesizes the existing `generated by` line and accepts the upstream JSON
slicer metadata envelope.

## Delivery and rollback

The production wheel compiles the native adapter for amd64 and arm64. Full and
lite images exercise both native metadata parsing and the separately supervised
official conversion CLI. No database or storage migration is required. Rollback
deploys the immediate parent image; Artifacts and stored metadata remain readable
because their schemas and serialized shapes do not change.

The controlled benchmark uses committed text and official BGCODE fixtures. It
checks identical source hashes and metadata before comparing the parent Python
implementation with the Rust implementation. Each profile measures a small text
file, a generated 18 MiB bounded-read file, the official BGCODE fixture, and a
malformed container, recording parser p50/p95/max latency, process CPU, process
RSS, and container peak memory.
