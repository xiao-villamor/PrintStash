# PrintStash 0.13.0 release and migration guide

Use this guide to prepare for or upgrade to PrintStash 0.13.0. Do not replace a
working installation without a complete rollback copy.

This guide starts with the upgrade itself, then covers the features that need
operator setup. The detailed storage rules remain in
[`UPGRADE.md`](../UPGRADE.md#0130-notes),
[`library-sources.md`](./library-sources.md), and
[`storage-data-safety.md`](./storage-data-safety.md).

## What changes in 0.13.0

### Storage becomes explicit about ownership and safety

PrintStash now records which provider and namespace own each managed object. It
probes the active storage and reports one of three safety tiers:

- **Verified** means the provider can prove create-only publication and the
  identity needed for safe cleanup.
- **Guarded** means publication is protected, but at least one proof needed for
  automatic physical deletion is unavailable.
- **Unguarded** means the provider cannot prove create-only publication. It
  requires an explicit startup acknowledgement and never qualifies for
  automatic physical garbage collection.

Local disk and generic S3 remain supported. New typed setup screens add Amazon
S3, Cloudflare R2, Backblaze B2, Wasabi, self-hosted S3, Nextcloud, WebDAV, and
SFTP. Provider support maturity and the measured safety tier are separate. The
remote presets remain beta even when a probe succeeds.

Apache OpenDAL is an internal transport in the full API image. It is used for
WebDAV and some remote-provider access. It is not a separate service and users
do not configure an OpenDAL URL.

### Existing folders can be indexed without handing over ownership

Library sources index files in place from:

- a directory mounted into the API container
- an S3 or S3-compatible prefix
- a WebDAV or Nextcloud collection
- an SFTP directory with a pinned host key

PrintStash stores catalog rows, metadata, and thumbnails. It never deletes the
source files. Remote sources are read-only. Mounted sources can optionally
accept create-only uploads and revisions.

### Browser capture keeps marketplace credentials in the browser

The browser extension pairs with a named, revocable device credential. It can
use the signed-in browser session to select Printables files, transfer a
MakerWorld package, or select individual Thingiverse files. Marketplace cookies
and credentials do not go to PrintStash.

Every capture enters Pending Imports for review. A completed import records a
Model Source snapshot with provenance fields and supports explicit user
overrides. MyMiniFactory OAuth and Cults metadata connections are per user.

### Multipart Models group existing Models

The Vault includes a Multipart Models view for objects made from several
printable Models. A Multipart Model contains ordered named parts. A part can
point to one fixed Model or offer several Model choices.

The grouping references Models already in the library. It never moves or owns
their Artifacts. Deleting a Multipart Model removes the grouping only.

### Print evidence and previews are more reliable

- Externally started Bambu LAN jobs retain the identity fields reported by the
  printer. PrintStash makes a bounded best-effort capture of exact G-code or a
  project 3MF while it remains in the printer's FTPS cache.
- Embedded 3MF previews take precedence when they pass the size and safety
  checks.
- Dense STL previews use a bounded streaming renderer before the sampled
  fallback.
- BGCODE uploads work from the main upload, drag-and-drop, and revision upload
  surfaces.
- GitHub-flavoured Markdown tables render in Collection READMEs and Markdown
  Documents.
- Administrators on the official supervised Compose deployment can restart the
  API from Settings.

## Choose your path

| Current installation | First 0.13.0 boot |
| --- | --- |
| SQLite and Compose named volumes | Keep the same Compose project name and volume mappings. Back up the database, secrets key, files, thumbnails, and backups together. |
| SQLite and host bind mounts | Keep the exact host paths and container paths. Set `PUID` and `PGID` to the positive numeric owner of those directories. |
| Generic S3-compatible storage | Keep `VAULT_STORAGE_BACKEND=s3` and every existing bucket, endpoint, region, credential, and root value unchanged. Do not choose a vendor preset yet. |
| PostgreSQL | Take an operator-managed `pg_dump` backup and snapshot storage. The built-in database backup does not support PostgreSQL. |
| Mounted library sources | Keep every mount unchanged. Expect to verify and enroll an eligible legacy source root before scans or watching resume. |
| Full API image | OpenDAL-backed WebDAV and SFTP providers are available. |
| Lite API image | Local and native S3 paths remain available. WebDAV and SFTP require a switch to the full image. |

The first boot is a compatibility boot. Prove the old configuration before
changing provider names, paths, buckets, or image variants.

## Before upgrading

1. Record the current image tag, Compose project name, database URL, storage
   settings, bind mounts, and external-library mounts.
2. Pause slicer hooks, imports, scheduled scans, and any other writer.
3. Create and download a fresh PrintStash backup if the installation uses
   SQLite.
4. Stop the API, then copy the SQLite database and
   `/data/db/.printstash-secrets-key` from the same point in time. PostgreSQL
   operators should use `pg_dump` instead.
5. Snapshot the managed files, thumbnails, and backup directory or bucket.
6. Back up every Library source separately. Linked source files are not included
   in a PrintStash backup.
7. Keep the previous image tag and the complete snapshot until the validation
   section passes.

The database, secrets key, and storage bytes form one rollback set. A database
from one moment and storage from another can refer to different bytes under the
same paths or keys.

## Upgrade the containers

When the release images are published, pin the version in `.env`:

```ini
PRINTSTASH_VERSION=0.13.0
```

Then pull and restart the existing stack:

```bash
docker compose pull
docker compose up -d --wait
docker compose ps
docker compose logs api
curl -fsS http://localhost:3000/api/v1/health
```

The API entrypoint runs the Alembic migration chain before serving requests. Do
not edit a migration or create an alternative schema. The 0.13.0 migrations add
records for provider identity, storage ownership, remote connections, discovery
cursors and tombstones, source verification, and garbage-collection plans. They
do not copy, rename, upload, or delete Artifact bytes.

## Validate the compatibility boot

Keep scheduled writers and retention disabled while checking the installation:

1. Sign in and open **Settings > Storage**. Confirm the expected provider,
   namespace, root state, and measured tier.
2. Download a pre-upgrade Artifact and load its thumbnail or preview.
3. Upload a small disposable Artifact, then download it again.
4. Open **Settings > Library sources**. Confirm every old External Library still
   points to the expected mounted path.
5. If a legacy root needs enrollment, inspect the exact path and visible files
   before selecting **Review and enroll**. Never create or edit a PrintStash root
   marker by hand.
6. Trash and restore a disposable Model. Do not approve permanent deletion of
   irreplaceable data during an upgrade test.
7. Create, verify, and download a new backup. Test restore in a separate recovery
   installation or disposable copy.
8. Run a manual Library source scan and compare the SHA-256 of one downloaded
   linked Artifact with its source file.

Read-only recovery is a safety state. If PrintStash reports a missing or
mismatched root, restore the original mount, bucket, endpoint, credentials, or
namespace. `VAULT_STORAGE_ALLOW_UNVERIFIED=true` does not bypass a root identity
error.

## Migrate each storage layout

### Local named volumes

Use the same Compose project name so Docker resolves the existing volumes. Check
the effective names before starting the new image:

```bash
docker compose config --volumes
docker volume ls
```

Do not create replacement volumes with similar names. If the stack was started
with `docker compose -p`, use the same project name during the upgrade.

### Local bind mounts and Unraid

The API image starts with the `10001:10001` identity unless `PUID` and `PGID` are
set. For bind-mounted application data, set both values to the positive numeric
owner that should access the directories. The entrypoint repairs ownership
before migration and rejects root or malformed IDs.

An Unraid user share that contains existing user-owned models normally belongs
in a Library source, not in `/data/files`. Map it into the API container as
read-only, for example:

```text
Host path:      /mnt/user/3d-library
Container path: /mnt/library
Access:         Read-only
```

After enrollment and a scan, users browse and download those files through
PrintStash. The API reads the mounted file and streams it to the browser or a
slicer. The same source remains available through Unraid's SMB or NFS share.
Only metadata and thumbnails live in managed Vault storage.

Unraid user shares are FUSE-backed. Use scheduled scans and recheck the mapping
after an array restart rather than depending on filesystem events.

### Existing S3-compatible storage

Keep the compatibility configuration for the first boot:

```ini
VAULT_STORAGE_BACKEND=s3
VAULT_S3_BUCKET=your-existing-bucket
VAULT_S3_ENDPOINT_URL=https://your-existing-endpoint
VAULT_S3_REGION=your-existing-region
VAULT_S3_ACCESS_KEY=your-existing-access-key
VAULT_S3_SECRET_KEY=your-existing-secret-key
```

The migration pins the historical `vault-data/` namespace. Do not rename or
copy that prefix. PrintStash no longer creates S3 buckets or changes lifecycle
policies, so the bucket must already exist. Existing credentials can drop
`s3:CreateBucket` and `s3:PutLifecycleConfiguration` after their data-plane and
read-only inspection permissions have been checked.

After the compatibility validation passes, switching to a matching typed
provider is optional. Use the same bucket, endpoint, region, address style, and
`vault-data` root. The switch changes configuration only. Version 0.13.0 does
not include a general provider-to-provider byte mover.

### Existing mounted library sources

Existing rows remain mounted sources, but scans, watching, and write-back may
pause until the exact root is enrolled. Verify the host mount from inside the
container:

```bash
docker compose exec api sh -c 'test -r /mnt/library && find /mnt/library -maxdepth 1 -type f | head'
```

Enroll only when the expected files are visible. A missing or wrong mount must
not be accepted as the old source.

### WebDAV, Nextcloud, and SFTP

Use the full API image. Configure a named provider through Setup or
**Settings > Storage** for managed Vault storage, or create an encrypted remote
connection under **Settings > Library sources** for a read-only Library source.

These roles are intentionally separate:

- Managed storage contains bytes PrintStash owns.
- A Library source contains bytes the user owns and PrintStash never deletes.

The official Compose files do not forward every new provider environment
variable from `.env`. Prefer the UI, or add the required
`VAULT_STORAGE_PROVIDER`, `VAULT_STORAGE_ROOT`, `VAULT_WEBDAV_*`, or
`VAULT_SFTP_*` fields explicitly to an API service override.

## Set up the new workflows

### Add a remote Library source

1. Open **Settings > Library sources** and enable the feature.
2. Create an encrypted S3, WebDAV, or SFTP connection.
3. Probe it before creating a source.
4. Add the source and optional prefix.
5. Run **Scan now** and download a representative linked Artifact.
6. Compare its SHA-256 with the source.

Remote scans are bounded and resumable. A source failure, empty namespace, or
unexpectedly large removal set cannot immediately remove catalog rows.

### Pair the browser extension

1. Build or install the extension version that matches the server.
2. Open **Settings > Imports** and create a pairing code.
3. Enter the Vault URL, code, and a device name in the extension within five
   minutes.
4. Open a supported model page and select **Send to Pending Imports**.
5. Review the detected files, Collection, tags, and source information before
   completing the import.

Existing browser pairings survive the upgrade. Rebuild and reload an unpacked
extension only if its displayed version is stale.

### Create a Multipart Model

1. Open the **Multipart Models** tab in the Vault.
2. Create the grouping and place it in a Collection if needed.
3. Add the first existing Model as a named part.
4. Add more parts in assembly order.
5. Add alternatives to a part when several Models can fill the same role.
6. Select a cover and attach a Multipart Guide when assembly instructions are
   useful.

Removing a member or deleting the grouping never deletes the underlying Model.

### Check Bambu LAN evidence

For a print started outside PrintStash, open its history entry and inspect the
evidence label. Exact means a matching G-code or project 3MF was captured from
the printer cache. Metadata means PrintStash retained printer-reported identity
but could not recover the file. Capture is best effort and time-limited by the
printer's FTPS cache.

## Garbage collection behavior

Scheduled retention now creates a bounded preview instead of deleting expired
rows immediately. Automatic physical deletion requires all of the following:

- Verified active storage
- a fully verified backup created within the previous 24 hours
- an independent S3 backup provider
- explicit approval of the exact plan digest
- completion of the configured quarantine period
- successful final revalidation

Guarded and Unguarded providers do not qualify for automatic physical garbage
collection. PrintStash retains bytes when it cannot prove that an exact object
is safe to delete.

## Roll back

Do not downgrade the migrated database in place.

1. Stop the 0.13.0 containers and every writer.
2. Restore the pre-upgrade database, secrets key, managed files, thumbnails,
   and backup storage together.
3. Restore separately backed-up Library source mounts when needed.
4. Start the previous image tag with its previous configuration.
5. Download a representative Artifact and verify a backup before reopening
   writes.

Root markers and ownership records created during the 0.13.0 run belong to the
upgraded rollback set. Mixing an older database with newer storage state is not
a supported rollback.

## Information to include in a support report

Include the following without posting credentials or signed URLs:

- previous and attempted PrintStash versions
- API image variant and CPU architecture
- database type
- storage provider, namespace, and reported tier
- Docker or NAS platform and filesystem
- whether the failure happened before or after root enrollment
- the health component and stable error code
- relevant API logs with secrets removed

Use [GitHub Discussions](https://github.com/xiao-villamor/PrintStash/discussions)
for migration reports and reproducible appliance notes. Use an issue for a
confirmed defect with repeatable steps.
