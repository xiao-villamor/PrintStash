# GPU render pilot

This is an optional tooling experiment. The application continues to use its CPU renderer. The GPU adapter is exercised through a narrow native-context fake in normal CI, so the suite requires no GPU library, display server or device. Those tests prove lifecycle, resource ownership, pixel transport and error classification; they do not prove GPU image quality, driver recovery or acceleration.

The CPU control uses current shared preparation and the same camera, material, supersampling, downsampling, compositing and encoder policy. Frozen inputs are available in the core `render-prepared-v1.json` corpus and backend `visual-prepared-v1.json`. Compare a reused GPU context against reused CPU preparation, rather than repeating CPU normal preparation for every view.

## Hardware qualification

Hardware observations are separate from the CI contracts. The [quality controls](../adr/0015-gpu-pilot/quality.json) and [recovery controls](../adr/0015-gpu-pilot/recovery.json) record root execution on a physical NVIDIA RTX 5060. A native API fake cannot supply this evidence.

- Compare the same complete visual flow with cold and reused contexts, including context/shader creation, source preparation, upload, completed drawing, readback and PNG/WEBP encoding. Record whole-child wall time separately from phase measurements. GPU host submission time is not completed device rendering time.
- Compare decoded RGBA and both RGB background policies against the independent CPU corpus. The visual policy is frozen before the first candidate image: the foreground mask at alpha >= 128 must match exactly, and maximum per-channel RGBA error must not exceed 8/255. Each protected part must retain a nonempty independently checked region. Repeated frames on the same GPU backend and across chunk sizes must be byte-identical. Check open surfaces, thin parts, holes, small remote parts, translated geometry and reflected instances independently of aggregate pixel scores.
- Record device/vendor/driver identity and distinguish software rendering from physical GPU execution. Record process RSS and observed device memory separately from requested buffer bytes; missing device telemetry must be explicit rather than zero.
- Exercise repeated sources and cleanup. A deliberately released context proves context lifecycle recovery, not recovery from a hardware reset. Injected allocation/driver failures prove classification and cleanup, not real device OOM or driver-crash recovery.
- Cancellation and deadline containment belong to the existing native supervisor. Actual child termination, reservation release and rejection of late output need their own root-run evidence; they are not proved by this adapter fake.

Adoption requires accepted visual quality and at least 1.5 times improvement in the complete visual flow for the declared hardware and source family, while retaining CPU operation and equivalent recovery. Preserve sample counts, failures and measurement scope. Missing hardware qualification means pending evidence, not a universal rejection of GPU rendering.

## Reproduce the optional experiment

Install the `gpu-pilot` extra in a disposable Python 3.14 environment. On platforms without current binary wheels, ModernGL/glcontext need a C++ compiler and platform OpenGL/EGL development headers. This is research tooling and is not a requirement for running PrintStash.

From `backend/`:

```sh
uv sync --extra gpu-pilot
uv run python -m scripts.gpu_render_pilot --case sharp-cube --flow multiview --trials 30 --memory-budget-mb 3072 --timeout-seconds 100 --output-dir /tmp/gpu-pilot-cube
uv run python -m scripts.gpu_render_pilot --case sphere-5120 --trials 1 --memory-budget-mb 3072 --output-dir /tmp/gpu-pilot-sphere
uv run python -m scripts.gpu_render_pilot --source /absolute/control.stl --trials 1 --memory-budget-mb 3072 --output-dir /tmp/gpu-pilot-stl
```

The host must have sufficient admitted memory for the requested allowance. On the measured WSL host, EGL required `GALLIUM_DRIVER=d3d12` and `MESA_D3D12_DEFAULT_ADAPTER_NAME=NVIDIA`. Other driver stacks require their own qualification; neither flag is part of application configuration. A `declined` experiment returns exit status 1 while preserving the CPU control, explicit failures and images in the output directory. The CLI creates and removes its own private vault, so it does not read or mutate the caller's library.

## Observed quality and containment

Fourteen canonical 640×480 controls were exercised once in each of the CPU-only, fresh-context and reused-context cells: ten public analytic controls and four anonymous private source controls. Both GPU modes accepted eight analytic controls, including the torus, open surface, thin solid, remote component, reversed winding, reflection, high translation and 200,000-face grid. A changed foreground pixel is not evidence of an entire missing component; protected-component visibility is a separate oracle.

Both modes refused sheared placement (RGBA/WHITE-RGB maximum difference 23), sphere-5120 (RGBA 228, WHITE-RGB 32) and all four private controls. Three private 3MF controls each differ by one foreground-mask pixel; the private STL has equal foreground coverage but a colour difference above eight. All fourteen independent CPU cells completed and all source hashes remained unchanged. Aggregate image equality does not replace the explicit protected-part checks needed for adoption.

The smaller immutable core corpus was also checked at chunks 1, 5 and 64,000. The tetrahedron, box and thin plate match their independent CPU RGBA references exactly. The 320-face sphere has one above-policy green-channel difference at a low-opacity edge (CPU `[194,194,220,18]`, GPU `[194,207,220,18]`). Its foreground mask matches, and the GPU result is stable across chunk sizes. No tolerance was changed after observing it.

A real context rendered alternating tetrahedron, box and thin sources nine times, retired, refused further use with the explicit closed reason, and a new context rendered the tetrahedron again. All ten RGBA hashes match independent frozen controls. Cancellation and a five-second deadline were then triggered during repeated real GPU rendering. The supervisor reaped each owned process group, accepted zero late reply bytes, and the following full-capacity admission succeeded. These are process/credit recovery observations; they do not qualify a physical GPU reset or real device OOM.

At a one-GiB allowance, the CPU-only control completed while GPU rendering caught a host `MemoryError` allocating the supersampled float64 depth array. At three GiB, the same product flow completed. A context-first probe at one GiB separately aborted in OpenBLAS allocation. These are real bounded host-memory failures, not demonstrated VRAM OOM. Requested attachment/buffer bytes, sampled process-tree RSS and device-wide baseline/end telemetry have different scopes. Context VRAM peak remains unavailable.

## Adoption assessment

Keep CPU rendering in the application. Measured speedups on a simple solid are promising, but image quality fails for the intended general STL/3MF family. Hardware-reset/device-OOM recovery and context-specific VRAM bounds remain unqualified. Do not introduce a production fallback, worker reuse across Artifacts, derivative recipe change or mandatory GPU dependency from this pilot. Future work can use its explicit deferred-frame and canonical encoder contracts.

## Complete visual cost

The corrected multiview measurement materializes the 3MF whole mesh, then prepares it through the production mesh owner. Counting only retained scene preparation omitted approximately 625–673 ms of loading/materialization and lazy imports on this host; the earlier optimistic series is superseded by the corrected series. Source/worker bootstrap overhead and protected-part qualification are not inferred from a raster timer.

| Cell | Samples per method | CPU derived full-cost median | GPU derived full-cost median | Ratio CPU/GPU | Outcome |
|---|---|---|---|---|---|
| Fresh context | 30 | 1,710.09 ms | 1,205.14 ms | 1.418991× | Below 1.5× |
| Reused context | 30 | 1,727.72 ms | 1,153.29 ms | 1.498073× | Below 1.5×; do not round into acceptance |

All 420 paired frame checks passed with exact RGBA/WHITE-RGB; GPU hashes were deterministic within each mode. CPU-only, fresh-context and reused-context whole-child supervised times were 34.39 s, 48.46 s and 45.95 s, respectively. Mixed cells include both the CPU and GPU control; those totals are not GPU-alone Artifact latency. Sampled process-tree RSS peaks were approximately 250/413/411 MiB respectively; they are not device allocations.

The retained-geometry medians were CPU/GPU 1,015.18/507.97 ms for fresh contexts and 1,006.16/429.28 ms for reused contexts. Those improvements cannot replace complete-source cost. The source is loaded once per cell; the full-cost column is a **derived estimate** which adds the measured common cold stages to every observation. Fresh-context observations run in one worker, so they do not establish isolated per-Artifact process startup latency. No p95 SLA is claimed from thirty samples. The first context, first encoder use and slow samples remain in the [raw observations](../adr/0015-gpu-pilot/samples.csv), with [summary and measurement scopes](../adr/0015-gpu-pilot/summary.json).
