# Derivative scheduling verification

A new upload must remain discoverable while backfill is active. Admitted backfill
must eventually execute under sustained interactive arrivals, including large
requests, without duplicating physical resource pools or consuming retry attempts
while it waits. Recovery must retain those bounds and durable intent.

`derive.native` and `derive.light` have one FIFO engine queue each. Discovery
reserves queued interactive allowance equal to lane concurrency, plus one active
backfill Job shared by every definition in the lane. The discovery fence locks
quota revalidation and Job creation in one transaction; submission follows commit.
Recent timestamp windows and an ascending keyset find interactive work, while a
frozen ID rotation and persisted turn protect backfill discovery. Physical native,
source-byte and I/O pools retain logical priority, with registration-order promotion
for backfill waiting at least 30 seconds. Active work is never preempted.

SQLite remains the default. The autogenerated application migration adds cursor
fields, closed-set/paired-position CHECKs, timestamp indices and a nullable
backfill admission epoch. It retains old
library rows and scan positions. No producer output or recipe changes here.
Before engine submission, a live lane fence commits a current-epoch backfill
reservation without spending an attempt. Exact-epoch submission rejects stale
or missing reservations; replay retains that owner across an unrecorded engine
acceptance or crash. Startup inspects legacy derivation engine ranks before enabling consumers; see
[the upgrade procedure](../../UPGRADE.md#unreleased-derivative-scheduling).

## Validation record

Focused runtime tests passed 92 cases, including the complete modified native
admission, native runtime, preparation runtime and Job runner files plus the
canonical priority scope. Discovery-cursor schema checks passed 8 SQLite/offline
cases and 7 real PostgreSQL upgrade/constraint/roundtrip variants.
Discovery/engine checks passed 166 cases. After adding durable reservation and
exact-epoch submission, the complete affected Jobs, source, reconciler and
submission files passed 226 cases. These include actual query plans at
1,000/10,000 historical Jobs, one cached owner SELECT per repair batch of 10/100
Jobs plus an authoritative scalar UPDATE per admitted backfill, real public
retry, accepted-before-recorded crash replay and busy-lane interactive progress.
Both real upload/native flows passed; the upload/backfill headline was also
rerun successfully after the final reservation change. Relevant
migration/schema/suite invariants passed 374 cases. Real PostgreSQL work checks
passed interactive admission, running-backfill quotas and existing fence/source
contracts. The backfill-reservation schema passed 14 variants initially; its two SQLite
ownership/roundtrip cases then passed after comparing reflected index predicates
as SQL text instead of object identity. A four-case final selection passed both
SQLite cases, real simultaneous PostgreSQL backfill admission and the updated
headline flow. Ruff lint, all 37 changed Python files, the 171-file CI formatting
scope and configured Pyright passed. Final relevant test-hygiene and schema-metadata checks passed 62 cases.

No full local backend suite, coverage lane, scale lane or Deep CI was run.
These are per-command case counts; overlapping checks are not added together.
Matrix status records the distinct asserted behaviours; the validation record
separately identifies checks that actually executed successfully.
