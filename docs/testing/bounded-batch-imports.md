# Bounded batch imports

A batch publishes each Artifact before materializing the next source entry.
`BatchSession` separates source identity, SQL confirmation and physical staging.
The entry ledger commits with the canonical File/Metadata/provenance transaction;
confirmation is independent of execution order and an Inbox retry Job id.

Production materializers use one disposable expanded/copied output at a time.
The configured positive file and byte caps are upper bounds. ZIP containers and
original leased uploads retain their separate existing limits. ZIP review still
validates the complete archive. Downloads are sequential; existing derivative
Jobs can start as soon as the first Artifact commits.

Processed counters advance during discovery; totals and percentages remain
unknown until expansion completes. A source failure does not discard earlier
Artifacts. Confirmed entries resume before resolver, download, hash or copy work.
Cleanup failure stops further materialization and leaves confirmed Artifacts
intact. Historical diagnostics survive superseded source placeholders while
current counts contain the selected expanded entries.

New accepted requests carry an internal identity-format version. They bypass
legacy indexed-key File lookup; the marker is hidden from selection consumers.
Unversioned stored requests retain a compatibility path. Multi-source adoption
requires a unique filename/SHA256 match against actual materialized bytes.
Reviewed standalone archives also require an exact original staging lease.

not opened after unsuccessful release. The E2E runs actual API review/select,
provider HTTP and Artifact download, with a finite gate on the second source.
SQLite and PostgreSQL upgrade tests use disposable databases with existing Jobs.
